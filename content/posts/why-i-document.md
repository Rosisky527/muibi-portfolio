Most of my early technical discipline came from a field with zero tolerance for undocumented systems: industrial automation, where a badly labeled control panel can cost hours during a breakdown. That habit carried straight over into how I write software.

## What I document, every time

Every project I hand off includes a README covering how to install dependencies, how to run it locally, where the important files live, and how to deploy it. It sounds basic, but a surprising number of handoffs skip this entirely and leave the next person guessing.

## Why it matters more for freelance work

When you're not going to be the one maintaining a project forever, documentation isn't optional politeness — it's part of the deliverable. A client (or the developer they hire after me) shouldn't need to reverse-engineer my folder structure to make a small text change.

## The five-minute rule

Before I consider a project finished, I ask: could someone with reasonable technical skill, who has never seen this code, get it running locally within five minutes using only what I've written down? If not, the documentation isn't done yet — even if the code is.

It's a small habit, but it's saved me (and my clients) hours down the line more times than I can count.
